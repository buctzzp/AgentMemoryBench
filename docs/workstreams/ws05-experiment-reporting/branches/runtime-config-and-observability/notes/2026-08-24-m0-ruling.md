## 1. Letta 的 `embedding=None` 到底是什么

结论分三层：

1. official `ai-memory-sdk v0.2.0` 的主用法默认
   `skip_vector_storage=True`。messages 驱动 standalone sleeptime agent 更新 attached core
   blocks；raw messages 不复制进 archival passages。官方只有显式改成 false 才启用 passage
   semantic search。
2. SDK 创建 sleeptime agent 时**省略** embedding 参数，不是显式传 `None`。vendored Letta
   server 的 `SyncServer.create_agent_async()` 会在请求没带 embedding 时尝试采用
   `settings.default_embedding_handle`；只有服务端也没有默认 handle 时，最终
   `embedding_config` 才保持 None。因此“官方省略”不能写成“官方推荐 None”。
3. framework current local profile 为避免 provider model sync，显式创建
   `embedding_config=None` 的 sleeptime agent；同时锁 `skip_vector_storage=True`、retrieve 只读
   全部 core blocks。真实运行中 initializer passage 以 `embedding=None` 存 SQL，build/retrieve
   均不调用 embedding。由于 core-block edit 本身由 LLM tools 完成，这不绕过当前主轨算法；
   但它是**项目受控 no-archival-vector 配置**，不是 upstream 推荐的通用 Letta 配置。

所以 controlled MiniLM 主比较对 current Letta 标记 `N/A`，而非强塞一个未消费的模型。未来若
增加 `skip_vector_storage=False + archival search`，它必须作为独立 product variant，配置
MiniLM、重建全部状态并重新裁 metric；不能借它给 current core-block 主轨补 Recall@k。

## 3. 已证实的效率缺口

current source 复核支持以下施工项：

- SimpleMem 的 HaluMem update probe 裸调 retrieve，阶段会落到 MEMORY_BUILD；
- MemoryOS 现有 LLM 观测完整，但 SentenceTransformer encode 尚无 observation；
- LangMem retrieve 的 config 未挂 usage callback，未来一旦 retrieve 内出现 LLM 会漏；
- Letta `_capture_usage` 在 collector buffer 未激活时静默 return；
- Mem0 current `rerank=False`，但内置 LLM reranker 若启用会另建 client 绕开现有埋点；
- 多家 transactional buffer 在操作失败时丢弃 observation，真实已发生 spend 因而不可见。

M2 必须区分算法状态回滚与成本事实：前者可以 discard，后者只能 append。
